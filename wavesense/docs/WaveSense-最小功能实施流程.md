# WaveSense 最小功能（MVP）实施流程（详细版）

> 范围：从 DEV202/DEV113P 毫米波开发板的**原始信号**到最小可用功能的执行流程。
> 硬件背景、预算、风险等完整信息见《WaveSense-项目精简文档.md》，本文档不再重复，聚焦"怎么做"。

---

## 1. 背景与最小功能目标

**硬件基础**：实验室发放 DEV202（1T2R，ICL1122）+ DEV113P（2T4R）开发板、2 个串口模组、2 份矽典微授权分析软件。

**数据链路**：开发板 → 串口模组连电脑 → 授权软件（波形 / 1DFFT / 2DFFT，导出 / 回放）→ Python 存在判定 → MQTT → Home Assistant。

**最小功能（4 项 P0）**：
1. 人在 / 离开检测（含静坐）；
2. 灯控联动：进入立即亮灯、离开延时 5 分钟关灯；
3. 进出事件记录（Logbook + 本地 SQLite）；
4. 本地网页仪表盘（人数 / 位置 / 灯状态）。

**验收指标（5 项）**：空房 1h 误报 = 0 ｜ 静坐 30 min 持续判定"有人" ｜ 双人判定计数 = 2 ｜ 灯控端到端 < 1 s ｜ 进出日志误差 < 2 s。

## 2. 三个候选步骤的取舍

| 候选步骤 | 是否需要 | 说明 |
|---|---|---|
| ① 把开发板初始数据转换为 XenP 成品数据 | **不需要（概念不成立）** | XenP"轨迹帧"是 ICL1122 固件在模块**内部**算好的输出格式，不是软件可转换的中间产物；DEV202 用同一颗 ICL1122，板内已内置 DSP/CFAR 处理链，授权软件直接给出处理后的数据（1DFFT/2DFFT/目标信息）。你要选的只是"用哪一层数据"：处理后的（推荐）或原始 I/Q（需自写 DSP/ML，时间不够） |
| ② 对成品数据进行分析 | **需要**（= S1 + S2） | 读授权软件可得的 1DFFT/2DFFT/目标信息 → 找可分特征 → 写存在判定 |
| ③ 把输出包装成美观的软件 | **需要"输出界面"，不必自研 GUI** | MVP 输出界面 = Home Assistant 仪表盘（现成、美观、可演示）；可选极简 Python 实时状态页（加分项，半天）；自研完整 GUI 不在 MVP 内（会吃 1–2 周且偏离课程核心） |

## 3. 核心原则（3 条）

1. **从最简算法开始**：存在判定用"阈值 + 去抖"，不先写复杂模型；
2. **每阶段有验证门（Gate）**：未通过当前 Gate 不进入下一阶段；
3. **日志 / 仪表盘最后做**：判定方案可能因数据特征调整，先做 UI 会反复返工。

## 4. 详细实施流程（5 阶段 · 14 子步骤 · 5 道验证门）

### S0 环境搭建与数据打通（D1 上午）｜ 产出：实时数据可读

| # | 子步骤 | 具体动作 | 完成标准 |
|---|---|---|---|
| 0.1 | 安装软件 | 找实验室要授权软件安装包 + 2 份授权码，装到采集电脑 | 工具能打开、授权正常 |
| 0.2 | 连接硬件 | 装串口模组驱动；USB 连接 DEV202、DEV113P；供电 | 系统识别 2 个串口设备 |
| 0.3 | 参数摸底 | 打开工具，记录两块板各自的帧速、距离门数、底噪、探测范围 | 参数记录表（用于后续阈值设计） |
| 0.4 | 数据可见性验证 | 空房 vs 挥手，观察波形 / 热图变化 | **Gate 1：有明显差异** |

### S1 数据理解与采样（D1 下午）｜ 产出：三类样本 + 特征结论

| # | 子步骤 | 具体动作 | 完成标准 |
|---|---|---|---|
| 1.1 | 确认可用数据层 | 弄清授权软件能直接看到/导出哪些数据：波形、1DFFT（距离谱）、2DFFT（速度谱）、目标信息 | 数据导出格式文档（CSV/文件格式） |
| 1.2 | 三类采样 | 用工具分别采集并保存 ≥5 min：**空房 / 有人静坐 / 有人走动**，标注场景与时间 | 每类 ≥1 份带标签数据文件 |
| 1.3 | 特征对比 | 对比三类数据的距离门能量、目标信息差异；确定判定特征（如"距离门能量和 > 阈值 = 有人"） | 特征选择结论 |
| 1.4 | 可分性验证 | 用样本验证静坐 vs 空房能否区分 | **⚠️ Gate 2（成败关键）**：可分则继续；不可分则降级"运动存在检测" |

### S2 存在判定脚本（D2）｜ 产出：presence.py

| # | 子步骤 | 具体动作 | 完成标准 |
|---|---|---|---|
| 2.1 | 定读数据通道 | 方式 A：实时读串口数据流；方式 B：先读导出文件离线验证（两者结合最稳） | 能稳定拿到一帧数据 |
| 2.2 | 脚本 v0 | Python 读取 + 打印特征值（能量 / 距离谱） | 特征数值与工具界面一致 |
| 2.3 | 脚本 v1 | 阈值判定 presence(0/1)，**先做运动检测**；连续 N 帧确认去抖 | 走动→有人、离开→无人切换正确 |
| 2.4 | 脚本 v2 | 叠加静坐判定：能量稳定 + 距离门持续占用 | 静坐 10 min 不误判为空房 |
| 2.5 | 联调 | 单人在 / 离开来回切换 10 次 | **Gate 3：切换正确率 ≥ 9/10** |

### S3 本地联动（D3–D4）｜ 产出：完整演示链路

| # | 子步骤 | 具体动作 | 完成标准 |
|---|---|---|---|
| 3.1 | 起 HA | Docker 起 Home Assistant + Mosquitto（旧笔记本即可） | HA 网页能打开 |
| 3.2 | 接入 MQTT | presence.py 增加 paho-mqtt，发布 presence / people_count 到本地 topic | `mosquitto_sub` 能看到消息 |
| 3.3 | 配置自动化 | HA 建实体 + 自动化：0→1 立即开灯；N→0 延时 5 分钟关灯 | 手动发布测试消息灯响应正确 |
| 3.4 | 日志与仪表盘 | 配 Logbook 进出记录 + 仪表盘卡片（人数 / 位置 / 灯状态 / 最近事件） | 页面完整可演示 |
| 3.5 | 端到端联调 | 真实进出场景跑通：进房亮灯、离开延时关灯 | **Gate 4：灯控端到端 < 1 s** |

### S4 测试与验收（D5 / W2–W3）｜ 产出：可验收 MVP

| # | 子步骤 | 具体动作 | 完成标准 |
|---|---|---|---|
| 4.1 | 边界测试 | 按 5 项指标逐项压测：空房 1h / 静坐 30 min / 双人 / 灯控延迟 / 日志误差 | 记录实测数据表 |
| 4.2 | 参数微调 | 根据测试结果调阈值、去抖帧数、安装角度/高度 | 指标达标 |
| 4.3 | 演示素材 | 录 3–5 段视频：进房亮灯、离开延时关灯、静坐持续、双人计数、仪表盘 | 视频存档 |
| 4.4 | 答辩材料 | PPT：架构图、数据链路、实测数据、取舍说明（如降级项） | **Gate 5：5 项指标全部达标** |

## 5. 关键验证点：Gate 2（静坐 vs 空房）

- **位置**：S1（第 1 天下午），是整个 MVP 是否成立的判定点。
- **做法**：用授权工具分别保存"空房"与"有人静坐看书"各 ≥5 分钟数据，对比 1DFFT / 2DFFT 的差异（能量、目标信息）。
- **结果分支**：
  - 可分 → 按完整方案继续（含静坐检测）；
  - 不可分 → 立即降级为"运动存在检测"（灯控/日志仍可演示），在答辩 PPT 中主动说明取舍。

## 6. 注意事项（3 个坑）

1. **S1 不要跳过**：静坐场景是相对 PIR 的核心卖点，也是开发板方案最大的不确定性，务必第 1 天实测；
2. **判定分层递进**：先让"走动→有人、离开→无人"跑通，再叠加"静坐能量稳定→有人"，一次到位风险高；
3. **联动依赖判定稳定**：灯控、日志、仪表盘全部依赖 presence 质量，判定未达标前不做 UI 和自动化调优。
